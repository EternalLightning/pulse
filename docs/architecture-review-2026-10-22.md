## 1. 结论与适用边界

Pulse 有渐进重构的必要。当前主要维护压力来自应用层状态与流程编排、`OpsManager` 的职责集中，以及预览运行状态和绘制之间的交叉。部分公共规则存在重复或差异，适合逐项收敛。

现有进程隔离、后台枚举、不可变快照、请求代际、对象身份保护和布局复用已经形成有价值的基础。网络盘增加了复杂度，但多数相关分支承担能力兼容、删除确认或对象安全职责，不能简单归为应删除的补丁。

建议先拆清职责和所有权，再整理公共机制，最后单独评估规则差异。以保持现有行为为目标，不能仅凭源码迁移或编译成功承诺功能完全不变。

本次审查：

- 阅读当前源码、相关未提交差异、构建依赖及已有定向测试入口。
- 没有实施重构，没有修改运行配置、替换安装程序或部署。
- 没有为本次审查构建或运行功能测试。
- 没有证明真实 RaiDrive、SMB 或第三方 Shell 扩展在全部场景下的运行行为。
- 下文的结构问题是维护成本与风险评估；除明确指出的规则差异外，不据此认定存在用户可见故障、可利用漏洞或性能退化。

## 3. Shell 当前结构与功能

### 3.1 进程和线程边界

```text
Pulse 主程序
├─ OpsManager
│  ├─ 文件操作队列、状态、撤销、重试、恢复日志
│  ├─ 原生复制／移动
│  ├─ 菜单转发线程
│  └─ 打开请求转发线程
│
├─ ShellClient → 常驻 Pulse.Shell.exe broker
│  ├─ Shell 文件操作：主 STA 与消息窗口
│  ├─ ContextSessionProcesses
│  │  └─ 每个菜单会话一个 --context-worker
│  │     └─ 协调 STA + 各注册处理器自己的 STA 线程
│  ├─ 普通 launch 池 → 每请求一个 --launch-worker
│  └─ 交互 launch 池 → 每请求一个 --launch-worker
│
└─ Shell 查询客户端 → 四槽复用池 → --query-worker
```

这些 worker 是同一个 `Pulse.Shell.exe` 的不同启动模式。文件操作提权另有操作 worker 入口。主要入口见 `src/shell_host/main.cpp:1466–1489`。

| 路径 | 功能与关键约束 |
| --- | --- |
| Shell 文件操作 | 执行需要 Shell 语义的操作，回传进度、结果和必要身份／删除证据 |
| 上下文菜单 | 查询、部分结果、迟到结果、动态子菜单、调用和关闭；同一 COM 实例与 STA 维持会话 |
| 打开请求 | 打开文件、属性、打开方式、注册表 verb、Reveal、命令等；请求完成后可能继续维持窗口或数据对象生命周期 |
| 交互请求 | 文件／目录选择和提权等待等；与普通 launch 分池，防止长期图片或属性会话占满交互资源 |
| Shell 查询 | 图标、显示名、类型名、快捷方式、PIDL／目录身份和预览初始化等；并非菜单查询器 |

菜单当前最多四个会话；launch 的普通池和交互池各有四条 runner、最多 64 个等待请求。查询池复用四个进程。这些限制服务于不同生命周期，不能为了复用而直接统一状态机。

### 3.2 值得保留的设计

- 菜单子进程隔离提供终止卡死 COM 的边界；每个处理器的 STA 线程使慢处理器不阻塞其他处理器先返回结果。两者作用不同。
- 普通 launch 与交互 launch 分池，避免长期会话阻塞选择器。
- `ShellClient` 只允许有限类别重放；删除、菜单调用和 launch 断线后不能自动重放，以免重复执行。
- 多窗口客户端具有请求所有者和回调生命周期管理。
- 无 handler worker 时获取系统汇总菜单的 fallback 仍在菜单 worker 内，并非退回 UI 加载危险扩展。
- 完成回包不必然代表子进程可以立即退出；可见窗口、消息循环、数据对象和图片会话可能继续存在。

关键位置：`src/ipc/shell_client.cpp:10–24`、`src/shell_host/main.cpp:655–671,1119–1227`、`src/shell_host/ctx_session_process.cpp`、`src/shell_host/shell_launch_process.cpp`。

### 3.3 是否存在很多特判

应区分软件名称政策、文件系统能力兼容和安全边界三类。

| 类型 | 当前实例 | 评价 |
| --- | --- | --- |
| 软件名称政策 | 识别 Bandizip、7-Zip、WinRAR、NanaZip、PeaZip 等压缩菜单；识别部分分享软件 | 确有特判，主要影响分类和菜单重组，适合集中维护 |
| Windows 协议适配 | Native New 的已知 CLSID、动态子菜单初始化 | 系统机制适配，应保留 |
| 身份查询能力兼容 | 扩展 ID 查询返回有限的“不支持”错误时，读取旧式 index | 按能力判断，不能改为任意失败都降级 |
| 网络删除分类 | UNC、远程盘类型、WNet 映射检测 | 业务安全策略，应保留并明确来源 |
| 虚拟文件系统身份变化 | Shell 枚举期间，保留对象与当前路径的实时 ID 同步变化 | 按对象行为判断，当前实现并非按 RaiDrive 名称放行 |
| 删除与撤销授权 | 网络永久删除确认、混合批次分组、最新 Copy undo 例外 | 保护用户授权和历史对象，不宜直接删去 |

软件名称识别集中在 `src/ipc/ctx_menu_util.h:290–332`。本次审查的主路径未发现按这些压缩软件品牌决定 IPC、超时或强杀的分支。

### 3.4 必须保留的网络盘和身份语义

1. **网络删除和本地回收分别执行。** 混合批次不能因为网络成员需要永久删除，就把本地成员一起改为永久删除。
2. **网络 Copy undo 的永久删除例外范围严格。** 当前要求最新且受支持的 Copy 历史、revision、目的路径和历史身份一致，相关物理目标均为网络路径，之后仍须冻结对象并取得确认。不能概括为所有 Undo 都允许永久删除。
3. **历史身份和保留对象身份是不同契约。** `FileObjectReference::Matches` 要求历史 ID、保留句柄实时 ID 和当前对象 ID 一致；`DeletionReference::Matches` 允许保留句柄与当前路径同步发生 ID 变化。可以共享读取原语，不能含糊合成一个默认比较规则。
4. **同名不等于同对象。** 大小写归一、重命名、确认期间替换和 reparse 目标都需要保持既有身份检查。
5. **回收恢复有独立契约。** 当前用户 SID、同盘 `$I/$R` 配对、原路径、身份和禁止覆盖等规则，不能用一般网络删除规则替代。
6. **永久删除回退必须重新确认。** 只有明确的回收失败类别才进入相关处理，不能将任意 Shell 错误自动改为永久删除。

关键位置：`src/ops/delete_operation.cpp:30–39,344–425,427–460,552–567`、`src/common/file_identity.h:27–45`、`src/ops/file_object_reference.h:32–36`、`src/shell_host/deletion_identity.cpp:24–63`、`src/ops/recycle_undo_validation.cpp:25–90`。

## 4. Shell 与文件操作的重构切口

### 4.1 拆分 OpsManager 的职责

`OpsManager` 同时管理文件任务、打开请求、菜单会话、撤销、冲突、重试、状态和恢复日志。菜单和文件操作共用的完成回包需要再次分流，说明外观接口与内部执行职责存在交叉。

建议保持对应用层的外部入口，先拆出菜单会话和打开请求管理，再逐步分离撤销历史、传输执行和日志存储。迁移时应随职责移动状态、线程和清理逻辑，避免只换文件位置。

证据：`src/ops/ops_manager.h:236–568`、`src/ops/ops_manager.cpp:1953–2317`。

### 4.2 从 Shell 入口抽出菜单会话引擎

`src/shell_host/main.cpp` 同时包含进程入口、broker 分发、文件操作、菜单会话及处理器线程。菜单部分已有可辨认的职责边界，适合整包移出，通过窄的发送回调连接 IPC。

应一起迁移会话数据、调用消息、session map 和生命周期，避免移出线程函数后留下跨文件隐式状态。

证据：`src/shell_host/main.cpp:769–1410`。

### 4.3 集中公共机制，保留不同执行策略

query、context、launch 中重复出现句柄 RAII、挂起创建进程、加入 Job、恢复运行、管道 PID 校验、父进程身份校验和连接处理。可以抽取小型底层工具。

重试、超时、关停、窗口存活和槽位释放策略仍应由各管理器拥有。launch 目前使用定义在 context 头中的通用窗口探测函数，也可独立为明确命名的共享工具。

### 4.4 网络路径观察与业务政策分开

删除分类检查 UNC、`DRIVE_REMOTE` 和 WNet 映射；撤销历史的 `session_only` 分类只检查前两项。这是当前存在的规则差异。

建议公共函数返回观察结果，例如 UNC、卷类型和映射状态，由删除和历史持久化分别决定政策。直接统一为一个布尔判断，可能改变 WNet-only 驱动的历史持久化行为。

证据：`src/ops/delete_operation.cpp:30–39`、`src/ops/ops_manager.cpp:1776–1793`。

### 4.5 回收站解析与目标保护分阶段整理

Shell 的 `ExactOriginal` 和文件系统层分别解析回收站 `$I`。旧格式字符串缺少终止符时，两者接受规则不同，已构成规则漂移。应先记录各自接受范围，再共享解析机制；改变接受规则应单独评估。

`DestinationGuard` 也同时包含快照比较、目录租约与提交、提权快照传输，可在外部入口稳定后按这三类职责拆分。必须保留各自的句柄共享模式及 reparse、硬链接和对象身份检查。

证据：`src/shell_host/recycle_fileop.cpp:58–84`、`src/fs/fs_recycle.cpp:48–53`、`src/ops/destination_guard.h:64–113,168–390,407–509`。

## 5. 应用层状态与流程编排

### 5.1 现有基础

`AppCore` 已将进程共享的偏好、收藏、暂存区和窗口注册等数据，与窗口自己的服务分开。设置、标签页、菜单等已有控制器；异步结果邮箱提供窗口关闭和结果身份保护。这些机制适合继续复用。

证据：`src/app/app_core.h:24–46`、`src/app/window_result_mailbox.h:10–49`、`src/app/settings_controller.h`、`src/app/tab_controller.h`。

### 5.2 AppState 和 Tab 的职责偏广

`AppState` 同时拥有导航、搜索、详情面板、拖放、动画、操作及异步请求状态。大量功能接受整个 `AppState&`，不同模块可以直接访问彼此的字段。

`Tab` 同时承载普通目录、压缩包、文件名搜索、内容搜索、选择和展示缓存。功能扩展需要理解大量状态组合。

建议按所有者逐步形成目录会话、搜索会话、选择状态、列表展示状态、详情会话和交互状态。对应模块负责转换与清理，应用层负责协调。单纯将字段套进结构体并不能解决所有权问题。

证据：`src/app/app_state.h:176–805`、`src/app/app_model.h:38–243`。

### 5.3 导航混合了多种数据源和更新流程

`app_navigation.cpp` 同时处理本地／网络搜索派发、合并、分页、内容搜索、虚拟视图、目录加载和目录通知。切换目录时，入口需要手动取消多个后端并清理各种请求状态。

建议先抽出搜索会话的启动、取消和结果接纳，再整理目录加载、通知合并和刷新协调。保留每种数据源现有的分页、订阅与取消语义。

证据：`src/app/app_navigation.cpp:265–734,752–1220,1431–1545`。

### 5.4 视图模型构造存在状态推进副作用

`BuildVm` 除构造显示数据，还同步窗口标题、更新可见性设置、同步列视图，并按条件提交详情元数据请求。命中检测也会调用它，通过参数关闭部分探测。

建议逐步分成状态更新与视图投影两个阶段：事件和后台结果负责更新状态、提交请求；视图构造从已准备好的状态生成绘制和命中数据。保留现有缓存及异步机制，使请求触发位置更加明确。

证据：`src/app/app_runtime.cpp:1532–1554,1857–1878,1965–1974`。

## 6. 界面与预览

### 6.1 值得保留的基础分层

`Compositor` 管图形设备和呈现，`fluent::Painter` 管通用控件绘制。列表的矩形、命中、可见范围和键盘移动使用 `ViewLayout`；工具栏和详情面板也在绘制与命中间复用布局函数。

这些机制能够减少视觉和交互位置不一致，后续重构应继续使用。

证据：`src/ui/ui_compositor.h:47–56`、`src/ui/fluent_components.h:347`、`src/ui/view_layout.h:48–69`、`src/ui/ui_toolbar.cpp:12`、`src/ui/ui_details_panel.cpp:42`、`src/ui/ui_hit_test.cpp:491,719,948`。

### 6.2 ThumbnailCache 跨越预览运行时和绘制

同一类启动／终止 `Pulse.Preview.exe`、处理 IPC 和共享内存、管理请求代际与缓存，同时创建 D2D 位图、裁切、绘制和修改视口。绘制接口还包含大量输入／输出指针。

建议先稳定请求和结果结构，再抽出预览进程客户端，随后拆分 GPU 资源和绘制。消费者兴趣、缓存代际、重试和取消语义保持不变。

证据：`src/ui/thumbnail_cache.cpp:155–254,350–490`、`src/ui/ui_details_panel.cpp:227–231`。

### 6.3 两个消费者分别管理预览策略和状态

详情面板与快速预览各自选择系统 handler 或 native 预览、提交请求、映射加载／失败状态。快速预览在 Render 阶段还提交 GIF 帧、更新播放状态和计时器。

可逐步引入消费者自己的预览会话，公共部分共享 provider 选择和状态快照；快速预览继续管理独有的视频／GIF 播放。

证据：`src/ui/ui_details_panel.cpp:196–255`、`src/ui/quick_preview_window.cpp:1138–1212`。

预览隔离需要准确区分：

- `Pulse.Preview.exe` 提供位图、文本／Hex和属性，控制／文本经管道传输，像素经共享内存传输。
- 系统 `IPreviewHandler` 经 `CLSCTX_LOCAL_SERVER` 激活，UI 侧保留 STA worker、overlay 和停滞管理。
- 现有请求期限、取消事件、响应校验，以及 epoch、request id、消费者 generation 检查，必须完整保留。

证据：`src/preview_host/main.cpp:690–740,809–858`、`src/ui/thumbnail_cache.cpp:350–366,436–453`、`src/ui/preview_handler_host.cpp:299–329,728–785,935–999`。

## 7. 索引、搜索与文件系统

### 7.1 当前边界

- 本地文件名搜索：`IndexClient` → named pipe → 索引 host → `Engine::Search`。引擎管理基础索引、内存 delta、MFT/USN 更新、查询和派生统计。
- 网络文件名搜索：`NetworkAgentClient` → 当前用户网络代理 → `NetworkIndex`。本地服务和网络代理使用同一个 `Pulse.Index.exe` 的不同启动角色。
- 内容搜索：客户端管理 agent 和取消，会话接纳分批结果、拒绝过期代际并维护分页结果；文档提取进一步进入独立的 `Pulse.Document.exe`。
- 文件系统：目录读取、不可变快照、LRU、generation、目录对象 identity、监听和 UNC 缓存各有相应模块。

这些隔离和生命周期边界应保留。尤其不能为统一接口，将文档解析、阻塞枚举或 watcher drain 移回 UI。

### 7.2 优先整理共享类型和结果编码

`Hit`、`Query`、`SearchResult` 与磁盘布局及 `Engine` 声明放在同一头文件中，协议头又直接包含引擎头，导致客户端在源码依赖上接触服务端内部声明。两个 host 还分别实现结果 payload 编码。

建议先抽取共享查询类型和结果编码，保持字段、默认值、顺序、限制和旧 trailer 兼容不变。这是依赖整理，不据此宣称性能提升。

证据：`src/index/index_engine.h:42`、`src/index/index_protocol.h:4`、`src/index/index_client.h:4`、`src/index/index_host.cpp:298`、`src/index/network_agent_main.cpp:52`。

### 7.3 澄清文件事实与列表行模型

`fs::DirEntry` 同时表示真实属性和虚拟列表信息，包括回收站 payload、历史变化文本、删除标记、快捷方式目标等；内容结果存储也直接使用它。

建议先集中适配，再按需要区分文件事实和虚拟行附加信息，迁移期保留兼容外观。历史记录不能作为实际文件操作源等限制必须延续。

证据：`src/fs/fs_enum.h:15`、`src/app/app_change_tracking.cpp:237`、`src/index/content_result_store.h:13`。

### 7.4 网络索引接口按实际并发需求演进

`NetworkIndex` 使用单个最新结果槽，网络 host 因而串行搜索、轮询结果，竞争时返回 `ERROR_BUSY`。这是旧异步接口被服务端适配产生的结构成本，本次未证明它造成了用户可见问题。

后续确有多窗口并发需求时，可考虑每次查询独立返回结果或完成回调，保留客户端外观、取消和错误语义。

证据：`src/index/network_agent_main.cpp:97`。

## 8. 模型、持久化与构建组织

筛选、查询解析、批量命名、命令可用性等已有相对独立的规则实现，应继续把无 I/O 的计算保持在明确模块中。收藏标签等模型仍有存储和异步保存职责，应按实际所有权逐步整理，不宜仅根据目录名假设全部都是纯模型。

设置控制器、标签页控制器和命令目录可作为后续应用层拆分的参考：由调用方提供能力或回调，明确状态和副作用的归属。

主程序构建目前广泛收集 app、model、ui、fs、ops、ipc、index 源码，再通过排除列表去掉服务端及测试实现。模块边界在较大程度上依赖约定维护。

建议随职责迁移逐步建立明确的模型、应用服务、预览客户端和搜索客户端目标，并让相关测试链接同一模块。每一步核对实际源码集合、资源和链接依赖，避免顺带改变程序组成。

证据：`src/app/command_catalog.h:9–29`、`src/model/item_filter.h:21–45`、`src/app/settings_controller.h:87`、`CMakeLists.txt:326–348,615–633`。

## 9. 建议实施顺序

下表表示依赖和收益顺序，不表示需要在一次改动中完成全部工作。

| 阶段 | 范围 | 主要验收边界 |
| --- | --- | --- |
| 1. 明确所有权与拆出会话 | 应用目录／搜索会话、OpsManager 菜单／打开管理、Shell 菜单会话模块 | 请求路由、取消、窗口关闭、迟到结果与现有 UI 行为保持一致 |
| 2. 分离状态推进与呈现 | BuildVm、详情会话、预览请求／结果结构与客户端 | 绘制和命中使用一致数据；预览代际、加载／失败、播放和交互不回退 |
| 3. 收窄公共依赖 | 查询共享类型、结果编码、菜单产品政策、进程和管道基础工具 | wire 格式、菜单分类、超时、重放、退出与槽位释放政策不变 |
| 4. 单独评估规则差异 | 网络路径分类、回收站解析、身份公共原语、DestinationGuard 内部拆分 | 明确每项保行为范围；确需改变的规则单独记录和验证 |
| 5. 配合模块构建演进 | 明确库目标、测试依赖、文件事实和虚拟行适配 | 生产源码集合和资源不遗漏，测试覆盖实际复用模块 |

每个阶段先迁移一个职责，再验证直接受影响的路径。避免同时修改协议、身份政策、缓存淘汰和交互行为，使回归来源难以定位。

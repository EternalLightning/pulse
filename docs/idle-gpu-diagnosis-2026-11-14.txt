Confirmed source paths for unnecessary periodic full-window repaint
- src/app/cloud_commands.cpp, TickCloudStatus: every two seconds an active
  cloud directory sets dirty even when the cached sync state did not change.
- src/app/app_change_tracking.cpp, TickChangeTracking/ReceiveChangeTracking:
  visible path summaries are queried every two seconds; any accepted mailbox
  response invalidates the window without checking whether the summaries
  changed. This path requires enabled change tracking and a response.

These are source-confirmed repaint paths, not a measured explanation of the
user's particular GPU reading. No production code was changed in this diagnosis.

Authorized fix and final verification
- Cloud status polling now visits the visible cloud detail rows from the last
  view model without drawing. The existing asynchronous provider/cache query
  and two-second maintenance gate remain; neutral results retain the existing
  ten-second cache refresh cadence.
- Cloud cache revisions now represent changes to the effective displayed
  state, with a per-file revision so offscreen/other-window results do not
  request a repaint of this window. A modified row whose cache became unknown
  still receives its non-neutral status when the background answer arrives.
- Change-summary results update the cache as before, but only changes to
  visible badge labels, deletion markers, colours or an open popover request
  repainting. Unchanged results, hidden tooltip-only changes, transient query
  failures and stale responses do not repaint. Maintenance still checks badge
  expiry independently of successful replies.
- Detail results preserve the existing snapshot when the generated rows are
  identical. Changed rows, visible error messages and empty states repaint;
  identical errors/empty responses do not. Background detail refreshes retain
  the current presentation while pending, and slow requests are not replaced
  by the periodic maintenance query.

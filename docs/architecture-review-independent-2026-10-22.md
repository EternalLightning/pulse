## 1. 总体结论

Pulse 已具备有价值的架构基础：Shell 和预览的进程隔离、后台目录读取、不可变快照、请求代际校验、多消费者请求共享、对象身份保护，以及绘制与命中检测的布局复用。这些机制应作为后续改进的约束保留。

当前值得处理的问题主要集中在以下接缝：

1. `OpsManager` 的菜单、打开和文件操作共用回调所有者，职责之间的生命周期依赖不够直观。
2. 导航入口承担多个搜索后端的取消和状态重置，搜索生命周期的维护入口较分散。
3. `BuildVm` 在构造显示数据时同步其他状态并提交详情请求，使读取视图数据的行为边界不够明确。
4. `ThumbnailCache` 同时负责进程通信、共享请求调度、缓存、GPU 资源和绘制，接口较复杂。
5. 索引客户端的公共查询类型与服务端引擎声明混放，协议头直接依赖引擎头。

这些问题支持局部、独立的整理，不足以支持一次全面架构重构。不能仅凭文件较长、字段较多、目录层次不够纯粹，就要求整体替换状态模型或建立更多框架。

建议先选择边界清楚、收益可解释的一个改动；对于涉及共享请求、关闭顺序和对象保护的部分，先写清契约，再迁移实现。完成条件应是责任更明确且相关行为得到验证，而不是类、文件或目录达到预设数量。

## 3. 当前架构与应保留的基础

### 3.1 主要职责分布

| 部分 | 当前职责 | 审查判断 |
| --- | --- | --- |
| 应用层 | 窗口、标签页、分栏、导航、搜索协调、命令及会话状态 | 主要维护压力在状态转换和异步生命周期交叉 |
| 文件系统层 | 后台枚举、快照、缓存、监听及目录身份 | 保留后台执行和结果接纳边界 |
| 文件操作层 | 复制、移动、删除、冲突、撤销、重试和恢复 | 安全契约有价值；菜单与打开管理可进一步明确归属 |
| Shell 客户端与主机 | 请求路由、菜单会话、打开、系统查询和部分文件操作 | 进程隔离及不同请求的生命周期策略应保留 |
| UI 与预览 | 布局、绘制、命中、预览请求、缓存和播放 | 布局复用合理；预览运行时与呈现接口可局部整理 |
| 索引与搜索 | 本地索引、网络代理、内容搜索、分页及订阅 | 保留后端差异，优先收窄公共类型依赖 |
| 构建与测试 | 主程序、隔离进程、公共库和定向测试 | 已有局部模块目标，适合按实际边界演进 |

### 3.2 不应被重构破坏的机制

- 阻塞文件系统操作、Shell COM 调用和文档解析保持在现有后台或隔离边界内。
- 结果接纳继续检查请求身份、代际、消费者状态和对象身份，不能仅以路径相同判定结果有效。
- 菜单、打开、交互和查询具有不同生命周期，不应为复用而统一超时、重放、退出和槽位释放政策。
- 多窗口关闭时只释放所属回调与状态，不影响其他窗口仍需要的共享服务。
- 绘制和命中检测继续复用布局规则，避免各自计算位置。
- 网络删除、本地回收、历史撤销和保留对象身份继续采用各自明确的安全条件。

## 4. 主要审查发现

### 4.1 OpsManager 的核心问题是回调所有权交叉

**源码确认。** `ShellOwner()` 从 `open_mailbox_` 获取 Shell 所有者；`StartShellClient()` 将打开完成、文件操作进度、操作完成和菜单结果回调注册到同一个所有者。`OnShellDone()` 再区分菜单调用、菜单查询与文件操作的完成结果。

因此，名义上属于打开请求的 mailbox 实际承载了多个职责依赖的回调生命周期。这比类的长度更能说明耦合问题。

关闭过程还存在不同约束：菜单线程等待退出；打开线程在有限等待后可以脱离，由独立 mailbox 保持其所需状态；文件操作线程通过取消、唤醒和等待完成退出。Shell 回调所有者的释放会等待正在执行的回调结束。

**建议。** 先明确回调注册、请求绑定和释放的归属，再迁移菜单或打开管理中的一个。可以保留应用层外观接口，但内部状态、队列、回调和清理逻辑应随职责一起移动。具体采用独立所有者还是显式共享协调对象，应由关闭契约决定，不在本报告中预设。

**边界与停止条件。** 不同步拆分撤销、恢复日志和传输执行，不引入通用任务框架。请求路由及回调释放责任清楚、关闭顺序可解释、直接相关用例验证后即可停止。

证据：`src/ops/ops_manager.cpp:974,2025,2030,2209`；`src/ipc/shell_client.cpp:50,67`；`src/ops/ops_manager.h:549`。

### 4.2 搜索生命周期应收拢，目录请求的共享关系必须保留

**源码确认。** `StartLoadingPath()` 负责取消本地索引、网络索引、内容搜索和压缩包工作，删除待合并搜索结果，并重置多组搜索及展示字段。增加一种状态时，需要同时理解启动、取消、导航和结果接纳路径。

目录加载又不是简单的标签页独占任务。`SharedListingRequest()` 在分栏和列视图之间复用请求；`CancelUnsharedListing()` 会先检查其他消费者是否仍在使用，再取消后台工作。

**建议。** 优先收拢搜索的启动、取消、重置和结果接纳，明确哪些字段必须一起转换。保留本地、网络、内容搜索各自的分页、订阅、取消与错误语义。

目录会话设计必须区分标签页拥有的展示状态、结果接纳资格，以及可能被多个位置共享的后台请求。不能把“会话销毁”直接等同于“取消底层任务”。

**边界与停止条件。** 不先行重建整个 `AppState` 或 `Tab`。当一个搜索生命周期的转换入口集中、清理责任完整且共享任务不会被错误取消时，即可结束该项改动。

证据：`src/app/app_navigation.cpp:882,896,910`；`src/app/app_model.h:38`。

### 4.3 BuildVm 的业务副作用值得优先约束

**源码确认。** `BuildVm()` 除构造显示数据，还同步窗口标题、显示设置和列视图，并按条件更新详情请求代际、清除旧数据及提交后台请求。`HitTestVm()` 也会调用它，通过参数关闭部分探测，但这并不使整个调用成为单纯读取。

**风险判断。** 调用者难以仅从视图构造接口理解其状态影响；后续增加绘制或命中调用时，需要额外判断是否会推动其他流程。

**建议。** 分别明确详情请求推进、窗口标题同步和偏好应用的触发入口。可采用事件驱动的更新入口或绘制前准备阶段，随后由视图构造读取准备好的状态。不能只覆盖鼠标和键盘输入，还要覆盖快照刷新、程序性选择变化及显示设置变化。

不要求所有呈现函数完全无副作用。GPU 资源准备、缓存填充和可见项登记可以保留在职责明确的呈现阶段。

**停止条件。** 命中检测不再触发业务请求，详情请求的提交条件可独立解释，绘制和命中数据保持一致。不以所有函数都变为纯函数作为验收目标。

证据：`src/app/app_runtime.cpp:1532,1858,1919,1965`。

### 4.4 预览可分层，但共享调度应继续集中

**源码确认。** `ThumbnailCache` 同时管理预览进程通信、请求队列、结果缓存、GPU 位图、裁切及绘制，绘制接口包含较多输入输出参数。与此同时，它已经提供跨消费者的内容请求去重、兴趣取消、结果代际校验，以及分别失效的设备资源。

`QueueRequest()` 合并相同内容键的请求；`CancelInterests()` 只有在没有消费者继续需要时才移除相关待处理工作；`StoreResult()` 校验服务代际、请求 ID 和消费者状态。`FrameScope` 则维护实际绘制范围对应的缓存兴趣。

**建议。** 先整理请求参数和结果结构，再按需要提取进程通信实现。详情与快速预览可以分别管理选择、可见性和播放状态，但应继续复用共享请求与缓存协调，不能自然演变为两个独立解码服务。

GPU 绘制是否继续拆分，应在前一步完成后评估。不能为了纯化绘制，将可见项登记随意移动到与实际绘制范围脱节的位置。

**边界与停止条件。** 保留请求去重、消费者取消、重试、缓存预算、设备恢复和陈旧结果拒绝规则。接口足够清楚、通信边界独立且行为可验证后，不必强制继续拆成更多组件。

已有测试源码包含跨消费者去重、关闭一个消费者保留另一个请求、代际切换拒绝旧结果等用例，应作为迁移依据。

证据：`src/ui/thumbnail_cache.h:25`；`src/ui/thumbnail_cache.cpp:21,39,82,129,350`；`src/bench/thumbnail_cache_test.cpp:429,444,460,483`。

### 4.5 索引共享类型适合独立整理，结果编码需要逐项核对

**源码确认。** `Hit`、`Query`、`SearchResult` 与磁盘结构及引擎声明位于同一头文件，协议头直接包含引擎头，使客户端的源码依赖接触服务端内部结构。

**建议。** 将共享查询类型移至独立头文件，保持字段、默认值和现有使用方式。该项不依赖应用状态或 Shell 重构，可以独立实施。

两个 host 的搜索结果编码具有重复，但并非所有表达式完全相同：本地 host 对命中数量直接转换为 `uint32_t`，网络 host 对该数量先做上限截断。这不证明合法输入下存在故障，但提取公共编码前，应核对输入上限、字段顺序、边界和旧 trailer 兼容行为，不能在去重时顺便改变策略。

**停止条件。** 客户端公共类型不再依赖引擎内部声明；若共享编码，合法输入输出及边界行为有直接证据。不能据此宣称获得性能提升。

证据：`src/index/index_engine.h:42`；`src/index/index_protocol.h:4`；`src/index/index_host.cpp:298`；`src/index/network_agent_main.cpp:52`。

### 4.6 Shell 菜单引擎具有迁移边界，不应借此统一所有 worker

**源码确认。** Shell 主入口中存在可识别的菜单会话数据、会话表、消息投递、处理器协调和结果发送代码。它们具有作为一组迁出的结构基础。

**建议。** 当菜单维护需要触及该区域时，可以将会话数据、线程协调、消息和清理一起迁移，通过窄接口连接发送能力。避免只移出线程函数，却保留跨文件隐式全局状态。

菜单、打开、查询和交互请求的存活条件不同。可以按已确认的重复提取句柄或进程启动原语，但不应设计统一 worker 状态机，也不应改变重放、超时和退出策略。

**停止条件。** 菜单会话状态与清理在明确模块中闭合，主入口只保留角色选择和转发即可。源码迁移不能证明第三方扩展调用后的资源已经释放。

证据：`src/shell_host/main.cpp:769,1351,1384`；`src/ipc/shell_client.cpp:10`。

### 4.7 安全与兼容规则应先澄清，不能因重复而统一政策

**源码确认。** 删除路径分类检查 UNC、远程卷类型和 WNet 映射；撤销历史的会话限定分类只检查前两项。两处服务于不同政策，存在差异不等于已经证明某一处错误。

两套回收站 `$I` 解析在旧格式终止符、长度、尾部字节、内部空字符和空路径等处理上也有差异。应先列输入与接受行为对照，再区分字节解析、列表展示和恢复授权的条件。

`DestinationGuard` 的快照、保留句柄、目录保护和提权验证共同维护对象保护契约。`CapturedIdentity()` 在存在保留句柄时重新读取身份，并非始终返回捕获时 ID；迁移不能把它改成单纯快照读取。

**建议。** 优先明确接口语义及行为对照，按需要共享读取或解析原语。保留历史身份与保留对象身份的区别，保留混合批次本地回收与网络永久删除的分组，以及回退重新确认规则。

**边界与停止条件。** 暂不将 `DestinationGuard` 拆成多个独立管理器。任何接受规则或删除授权变化应作为独立行为改动审查，不能隐藏在架构整理中。

证据：`src/ops/delete_operation.cpp:30`；`src/ops/ops_manager.cpp:1776`；`src/shell_host/recycle_fileop.cpp:58`；`src/fs/fs_recycle.cpp:22`；`src/ops/destination_guard.h:85,145`。

## 5. 应暂缓或避免的重构

| 候选方向 | 当前判断 | 重新考虑的条件 |
| --- | --- | --- |
| 全面拆分 AppState、Tab | 聚合状态本身不是缺陷；先收拢写入口和转换规则 | 已有明确的跨模块写入问题，局部收拢仍无法控制 |
| 全面替换 DirEntry | 牵涉枚举、虚拟视图、选择和操作消费者，迁移面较大 | 操作资格与路径适配集中后，仍存在具体语义混淆 |
| DestinationGuard 多组件化 | 可能将完整保护契约变成调用方必须维护的顺序 | 有独立复用或验证需求，并能明确保留完整保护条件 |
| 统一进程或 worker 框架 | 容易抹平菜单、打开、查询的生命周期差异 | 多处稳定机制确实相同，且可用小型工具表达 |
| 网络搜索立即改为并发 | 现有串行适配有结构成本，本次未证明用户影响 | 实际多窗口并发或延迟证据表明需要改进 |
| 按目录全面建立库目标 | 目录不必然等于模块；增加目标也可能增加依赖维护 | 存在明确依赖边界或生产与测试实现复用需求 |
| 所有绘制函数完全纯化 | 可见性、缓存和设备资源与呈现阶段关联紧密 | 特定副作用造成可说明的问题，且迁移不会增加同步负担 |

`DirEntry` 中历史记录、回收站 payload 和快捷方式目标的语义应先通过明确适配与操作资格检查约束。不能仅以字段数量作为更换模型的理由。

网络搜索当前使用互斥保护单结果槽并轮询等待，竞争时可返回忙状态。该事实支持保留为候选改进，不支持直接认定存在性能故障。

证据：`src/fs/fs_enum.h:15`；`src/index/network_agent_main.cpp:97`。

## 6. 构建边界与线程边界

### 6.1 延续已有模块约束

主程序存在广泛收集源码并排除部分实现的构建方式，但也已经建立 Shell 查询、Shell 交互、文本、存储等公共目标，以及 UI 包含依赖检查。

`tools/check_ui_dependencies.py` 检查 UI 是否通过直接或间接项目包含到达应用层，可作为现有边界约束继续使用。构建整理应配合已经明确的模块边界，而不是按目录机械分库。

新增模块目标时应核对生产源码集合、资源、编译选项和链接依赖；相关测试在合适情况下链接同一实现，避免另行复制形成偏差。不要求每次职责整理同步修改整个构建体系。

证据：`CMakeLists.txt:289,298,326`；`tools/check_ui_dependencies.py:1`。

### 6.2 区分后台监听与 UI 结果接纳

底层监听、阻塞等待及文件系统读取应保持在后台。UI 线程接纳已经排队的通知并更新界面状态，则是合理的职责。

当前窗口定时器调用 `DrainDirNotifies()`，协调通知合并和状态更新。不能笼统要求将所有“drain”移出 UI，也不能借统一接口把底层阻塞工作移入 UI。是否存在过量接纳导致的延迟，需要另有运行证据，本次未测量。

证据：`src/app/app_main.cpp:1096`；`src/app/app_navigation.cpp:1431`。

## 7. 建议优先级与实施方式

以下为独立候选项，不构成必须依次执行的全量重构计划。

| 优先级 | 候选范围 | 最小切入点 | 主要验收依据 |
